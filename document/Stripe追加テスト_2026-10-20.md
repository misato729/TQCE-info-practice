# Stripe追加テスト（2026年10月20日）

## 確認範囲

実際のStripeサンドボックスとローカルアプリで確認した。公式の架空テストカードのみを使用し、実課金、本番DB・本番Stripe設定の変更、販売開始は行っていない。

公式CLIで受信した実イベントの本文と署名を変更せず、確認用中継からローカルのWebhook受信APIへ転送した。署名検証やアプリの処理を省略していない。

## 結果

| 確認項目 | 結果 |
| --- | --- |
| 決済完了通知の遅延 | Stripeで支払済みでも、通知を保留している間は決済`pending`・資格なし・有料問題HTTP 403を維持した。再購入はHTTP 409、画面は「決済の反映を待っています」と表示した |
| 遅延後の復旧 | 保留した通知を2回転送してHTTP 200・200、資格1件、有料問題HTTP 200となった。「もう一度確認する」で完了表示へ遷移した |
| 通知順の逆転 | 返金通知を決済完了より先に転送するとHTTP 500となり、処理済み記録は残らなかった。決済完了を処理した後で同じ返金通知を再転送するとHTTP 200となり、返金済み・資格停止・有料問題HTTP 403に整合した |
| 非同期返金失敗の再現 | 一度`succeeded`になった返金が後から`failed`となる実通知を受信した。修正前はStripeの成立済み返金額が0円へ戻っても、アプリには500円返金済み・資格失効が残る不具合があった |
| 修正後の再確認 | 別のテスト決済で実際の`refund.failed`を2回転送してHTTP 200・200、イベント記録1件、返金額0円・決済`paid`・資格`active`・有料問題HTTP 200となった。失敗理由と日時の保存、アカウント画面の有料会員表示も確認した |

## 修正内容

`refund.failed`でStripeの現在のChargeを照合し、成立済み返金額・全額返金日時・決済状態を整合させる。同じ購入の返金だけを理由に失効した資格に限り、全額返金や異議申立てが残っていなければ元へ戻す。購入元と当初の有効化日時は維持する。

別購入の資格、異議申立てによる失効資格は復旧しない。照合通信が失敗した場合はDB更新とイベント記録をロールバックし、再試行できる状態を保つ。DBのカラムや公開APIは追加していない。

関連仕様は[要件定義](要件定義.md)、[API設計](API設計.md)、[DB設計](DB設計.md)、[運用手順](運用手順.md)へ反映する。

## 回帰確認

関連自動テスト64件が成功し、失敗・エラー・スキップは0件だった。対象はCheckout、Webhook、未完了Checkout失効、運用点検、決済・会員情報・お気に入り・問題取得APIである。

2026年10月21日、別作業の未コミット変更を含めず、コミット対象だけを分離したコピーでも再実行し、64件・294アサーション、失敗・エラー・スキップ0件を確認した。

別の全額返金が成立している場合、紛争が記録されている場合、Stripe側に紛争がある場合、資格の購入元が変わっている場合には誤って復旧しないことも確認した。Chargeの不一致や通信失敗では処理済み記録が残らず、再試行できることを検証した。

## 制約と残件

- Stripe Dashboardの再送ボタン、本番Webhook配送、Stripe側の自動再送、外部障害通知の到達確認は未完了とする。確認用中継からの再転送で代替したことにはしない。
- Webhook本文と署名は中継プロセスのメモリだけで扱い、記録やGitへ保存していない。
- 確認用アカウントをログアウトし、中継・公式CLIの停止と待受ポートの閉鎖を確認した。既存会員の決済は変更していない。
- 試験後に本番の公開設定APIを再取得し、販売が無効であることを確認した。コードのpush、バックエンドへの配信、本番設定の確認、販売開始はそれぞれ区別する。
- 本番販売を有効にするには、残件の解消と所有者の別途承認が必要である。

実施結果と残件は[Issue #6](https://github.com/misato729/TQCE-info-practice/issues/6)で管理する。監視・通知の残件は[Issue #8](https://github.com/misato729/TQCE-info-practice/issues/8)で管理する。
