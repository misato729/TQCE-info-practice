# 移行後のUI・API総点検（2026年10月24日）

## 範囲と制約

移行直前の `dbdfbbd^`、現行実装、要件・画面一覧・API設計を照合した。認証方式のBetter Auth化、Prisma化、既存ユーザー等のリセットは承認済みの変更として区別する。問題・選択肢は変更しない。Netlifyのデプロイ、リモートPRの更新・再実行、commit・push・mergeは実施しない。重い確認は直列実行し、DBテストは通常の開発DBとは別の `_test` DBに限定する。

## 見つかった退行と修正

| 項目 | 原因・対応 |
| --- | --- |
| 試験セットの幅・表示数 | 静的HTMLの読込中classがhydrate後に残り幅が縮小。設定の50セット×20問を初めから固定描画し、Sidebar自身の認証待ち・API呼出しを除去。公開可否・有料認可は問題APIが判定する。 |
| API正常時の黄色ドット | 静的HTMLのidle classと正常textが混在。mount前の表示状態をidleへ統一し、mount後に同じ状態からclass・textを更新。確認専用APIは追加しない。 |
| 初回会員表示のリンク | 静的ページでマイページ表示なのにhrefが/login、有料模試のhrefが/premiumのまま残ることを再現。初回のSSR hydration中だけ認証反映をNuxt公式onNuxtReadyまで遅らせ、共通ヘッダー・ホーム・会員案内をSSRと一致させてから個人化する。保護されたCSR画面の認証待機とSSR no-storeは維持。 |
| 管理ログイン入力欄 | 子コンポーネント化でscoped CSSが入力へ届かず、アイコンと文字の余白が失われる。deep selectorで39pxの左余白を復元。 |
| 同じユーザーの再ログイン後のお気に入り | native認証の世代更新で旧取得応答を破棄した後、同一ユーザーでは再取得しなかった。お気に入り・履歴の監視に世代を追加し、履歴の古い応答を破棄。旧401から新セッションを守る世代ガードは維持。 |
| 別タブでの認証・資格変更中の演習 | Cookie認証ではauthHeadersが変化しないため再取得が起きなかった。本人・資格・有効な認証世代の変更を監視し、旧問題・回答・履歴表示を破棄して再取得。遅い回答を新会員へ反映しない。匿名401の再取得ループは防ぐ。 |
| 無効・失効した認証付きの無料回答 | 旧仕様では401だったが匿名回答200となり、履歴が保存されない恐れがあった。Better Auth公式Cookie検知とsignOutによるCookie失効を使い401を返す。認証Cookieなし・無関係Cookieの匿名演習は維持。 |
| 文言・既定タイトル | 削除警告、お気に入り案内、paywall、既定タイトル、Checkoutの日本語価格表記を移行前へ合わせて復元。設定・販売無効時の分岐は維持。 |
| 復元リハーサル | shellが消えたRailsサービスを呼んでいた。現行frontendコンテナのNode CLIと同梱pg_dump/pg_restoreへ切替。ローカル許可名にnuxt-dbを追加。 |
| ローカル検査のDB接続ガード | 旧サービス名dbだけが許可され、新名nuxt-dbでマイグレーション検査が拒否された。隔離テストの許可ホスト名を現行Composeへ合わせた。 |

## 維持を確認する契約

- 問題URLは `/practice/{examNumber}/{questionNumber}`。回答前に正答・解説を返さず、公開範囲・有料資格は各APIで検査する。
- 問題文・選択肢のcontent_blocks、scope・複数模試/問番号・順序/seed、次問導線を維持。
- 本人だけの履歴・お気に入り、一般/管理の同一認証、現在DBのadmin role検査を維持。
- Stripeの一回買い切り、価格・通貨・所有者・署名・live/test照合、二重処理防止、返金・異議申立て処理を照合。実Stripeや新しい販売は今回使用しない。
- 実問題のseed・再投入は行わない。通常のローカルDBの問題1,000件・選択肢4,000件を保全する。

## 意図的な差・残る注意

- 管理入力の試験番号上限は設定の50。旧Railsは任意の正整数を許可したが、現構成では51以降を作る前に設定更新が必要になる。今回は設定正本・固定50の方針を維持する。
- Bearer tokenからHttpOnly Cookieへ認証方式を変更し、旧ログイン経路を残さない点は承認済み。初回はBetter Authのセッション確認とアプリの本人情報取得を使う。試験一覧・接続状態確認のための専用通信は行わず、既知の匿名状態を理由に同じ本人確認を強制再取得しない。
- 別タブのログインはBetter Auth標準のフォーカス復帰時の同期に従い、5秒間隔の再確認制限がある。ブラウザテストではDateだけを進めてこの標準経路を再現し、アプリ独自のポーリングを追加しない。
- 不正IDを匿名で管理APIへ指定した場合の401/404判定順には差がある。正規の管理導線・認可は維持する。
- Netlify経由のIPレート制限が共有され得る制約は既存の運用資料に記載済み。今回ネットワーク構成を変更しない。

## コンテナ起動

現行は `frontend`（Nuxt画面＋Nitro API）と `nuxt-db`。旧Railsのbackendサービスは通常起動しない。

- 画面: http://localhost:3000/
- API: http://localhost:3001/api/v1/health
- frontend上限: メモリ1536MiB、CPU1.25、Node heap768MiB。DB上限: 256MiB、CPU0.5。
- ビルド/起動の並列度を2へ抑制。ブラウザテストはNode heap1024MiB・1ワーカーで実行する。
