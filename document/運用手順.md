# 公開前の設定・運用手順

対象: Issue #6〜#9。手順の整備と実サービスでの検証完了は区別する。実施結果は [公開前運用確認](公開前運用確認_2026-10-20.md) に記録する。

## 変更しない前提

- 公開前はNetlifyの本番・プレビューをPrivateにする。Fly.ioのAPIは別の公開口であり、CORSだけでアクセスを制限できるとは扱わない。
- 販売開始の承認と下記の確認が完了するまで `PAID_MEMBERSHIP_ENABLED` を有効にしない。
- 2026年10月21日に問題完成・seed廃止が承認された。通常リリースは `db:prepare` のみとし、本番DBを正本に管理画面で編集する。15分のrelease timeoutはDB準備の上限として維持し、問題の自動投入・同期を追加し直さない。
- デプロイ、バックアップ確認、決済照合だけを理由に、本番問題・会員・履歴を削除しない。

## 読み取り専用の点検

バックエンドで `bin/rails operations:audit` を実行する。本番ではFly.ioの対象アプリへ接続してから実行する。追加の公開APIやフロントエンドのポーリングは設けない。

出力は設定不足の項目名、販売の有効・無効、集計件数、警告名と確認日時だけとする。メールアドレス、ユーザーID、Stripe ID、DB接続文字列、秘密値は出さない。DBトランザクションは読み取り専用で、Stripeへの通信や決済・資格の変更は行わない。

| 項目 | 確認内容 |
| --- | --- |
| `payment_configuration_issues` | 必須設定の不足、キーと実行モードの不一致、戻り先URLの不正、本番のテストモード |
| `stale_pending_checkouts` | 作成から24時間以上経過した未完了決済。障害と断定せず、Stripe上のSessionと照合する |
| `refund_failures_last_day` | 過去24時間に返金失敗を受信した決済 |
| `disputed_payments` | 異議申立て状態の決済。解決済みでも手動確認待ちを含む |
| `active_memberships_with_revoked_payment` | pending・expired・refunded・disputedの決済を根拠に有効になっている資格 |
| `processed_webhooks_last_day` | 過去24時間の処理済みWebhook件数。0件だけでは障害と判断しない |

警告がなければ終了コード0、決済状態に確認対象があれば2、実行自体の失敗は非0とする。販売を止めている期間の設定不足は、障害ではなく販売準備の残件として扱う。定期実行と通知は別途設定が必要で、このコマンドを追加しただけでは有効にならない。

## Stripeの販売開始条件

1. Stripeのテスト環境で、購入成功、未完了・取消、同じWebhookの再送、重複購入防止、全額返金、異議申立てを確認する。ローカルの模擬応答テストと実Stripeの試験は分けて記録する。
2. 本番のProduct・Priceが日本円500円・一回払い・有効であることを確認する。`STRIPE_SECRET_KEY`、Price、Webhook送信先・署名シークレットを同じ本番モードにそろえ、`STRIPE_LIVEMODE=true` とする。
3. `FRONTEND_URL=https://johokyonin-lab.netlify.app` とする。成功時は `/premium/complete`、取消時は `/premium?canceled=1` に戻る。HTTPSのオリジンだけを指定し、認証情報、パス、クエリ、フラグメントを入れない。ローカルのHTTPはlocalhost/127.0.0.1だけを許可する。本番ドメインを変更するときは `CORS_ORIGINS` も同じオリジンへ切り替え、旧オリジンの拒否と新オリジンの疎通を確認する。
4. Webhook送信先は `https://tqce-info-practice.fly.dev/api/v1/webhooks/stripe` とし、README記載の7イベントを登録する。署名不正400、正しい通知200、再送時の非重複を確認する。
5. 販売者名、責任者、住所、電話番号、連絡先、提供内容・時期、返金条件、利用規約とプライバシーポリシーを運営者が最終確認する。仮の連絡先や架空の事業者情報では開始しない。
6. バックアップ・復元、監視通知、HTTPS・認可、応答性能の公開前残件を解消する。運営者が販売開始を承認した後にだけ販売フラグを有効にする。
7. 有効化後に公開販売設定と導線を確認する。本番の実決済が必要なら金額・実行者・返金の扱いを先に承認し、検証用資格で代用したものを購入試験済みとしない。

販売設定に問題があればフラグを無効へ戻す。既存購入者の資格を一括で削除したり、支払済みの記録を手動作成したりしない。キーや事業者情報の値はIssue・コマンド履歴・ログへ貼らない。

## Webhook・決済の障害対応

| 状況 | 確認と対応 |
| --- | --- |
| Checkoutで502 | Fly.ioの時刻・request IDと `Stripe Checkout Session creation failed` を確認。Stripe側の障害・キーとモード・通信状態を確認する。連打で別決済を作らない |
| Webhookで400 | 署名、対象endpoint、実行モード、金額・通貨・metadataの照合を確認。署名検証を外して通さない |
| Webhookで500 | `Stripe webhook processing failed` と例外クラスを確認。Stripe Dashboardの対象イベントと送信履歴を照合する。DB更新はロールバックされるため原因を解消して再送する |
| 支払済みなのに資格反映待ち | Stripe上のSession・PaymentIntent・対象ユーザーの対応を権限のある画面で確認する。対象の署名済みイベントを再送し、同じEvent IDで重複がないことを確認する |
| 非同期の返金失敗 | 失敗理由と受信日時に加え、Stripeの現在の成立済み返金額と決済状態を照合する。同じ購入の返金だけによる資格失効は、全額返金・紛争が残っていなければ自動で元へ戻る。紛争や別購入の資格は自動で戻さない。照合通信が失敗した場合は処理済みとせず再送する |
| 返金・異議申立て | 決済とStripeの状態を照合する。全額返金・異議申立てで資格を停止する仕様を維持する。異議申立て終了後の資格再開は自動では行わない |
| 24時間超のpending | Sessionを取得して未完了・expired・completeを確認する。既存の `PendingCheckoutExpirer` の仕様に従う。支払済みを単にexpiredへ書き換えない |

再送はStripe Dashboardの対象イベントから同じ送信先へ行う。本文をコピーして署名を偽造したり、DBへ有料資格だけを書き込んだりしない。再処理後は決済1件・購入資格1件、処理済みEvent IDの重複なしを確認する。テスト環境で先に実施し、本番への金銭操作やデータ修正は個別に承認する。

### 監視の現状と未設定事項

担当はリポジトリ所有者を一次窓口とする。追加費用0円・メール通知を前提とし、通知先の実値は公開資料へ記載しない。

- バックアップの日次状態通知は個別承認後に有効化し、手動実行の正常通知と、架空データによる障害・復旧メールの受信を確認済み。定期起動の継続と試用終了後の無料プランでの継続は別途確認する。
- APIの障害通知は実装の本番反映まで確認したが、外部送信は無効。本番有効化・到達試験・許容する検知遅延は残件。既存のバックアップ通知の承認を流用しない。
- API healthの定期ポーリングやFly.ioの常時起動は設定しない。利用時のエラー通知と、利用がない時間帯の完全停止の即時検知は区別する。
- 決済集計の日次点検は残件。既に確認済みの異議申立てを毎回新規障害として通知しない。
- 日次処理とAPIの通知は分け、利用者情報・接続情報・リクエスト本文を送らない。詳細設定は専用の非公開リポジトリ、公開可能な結果は [公開前運用確認](公開前運用確認_2026-10-20.md) で管理する。

### API障害通知（実装反映済み・外部送信無効）

2026年10月21日、Railsのリクエスト完了通知を利用する `ApiErrorNotifier` を追加した。SDKによる自動収集は導入せず、送信データを新規に組み立てる。ローカルの偽HTTP接続で検証し、同日午後に実装の本番反映と送信無効を読み取り確認した。実Sentryへの送信やSecret登録は行っていない。

| 設定 | 初期値・用途 |
| --- | --- |
| `ERROR_NOTIFICATIONS_ENABLED` | `false`。文字列 `true` の場合だけ送信する |
| `SENTRY_ERROR_DSN` | 未設定。承認したSentryプロジェクトの送信用DSN。バックエンドのSecretにだけ設定する |
| `ERROR_NOTIFICATION_ENVIRONMENT` | `verification` 又は `production`。未設定はRailsの環境に合わせる |

- 対象はAPIコントローラーまで到達したHTTP 5xx。一般API・Stripe API接続・Webhook処理の固定3種類に分ける。販売停止やWebhook未設定で予定どおり返す503は除く。ルーティング前・起動時・ネットワーク断・利用がない時間帯の停止は検知できない。
- 送信は `message`（固定の障害名）、`timestamp`、`event_id`（ランダムID）、`environment`、`level` の5項目だけ。リクエストや例外のオブジェクト・本文・接続情報は渡さない。送信先はSentryのHTTPS取り込み先に限定し、リダイレクトを追わない。
- 有効化後は対象の最初の失敗で送信を試み、同じ種類・環境は1プロセスにつき1時間に1回までとする。DB障害でも通知を試せるよう、通知の抑制はプロセス内で行う。再起動でリセットされ、マシン数にも比例するため、Sentryアカウント全体の厳密な上限ではない。失敗した送信もその時間窓では再送しない。
- 接続・読み込み・書き込み・TLSのタイムアウトは各1秒、HTTP自動再試行なし。通知失敗で元の応答やStripe再送の意味を変えず、固定の失敗名だけをログへ出す。通常の成功や4xxでは送信しない。
- 自動解決・復旧メールは未実装。一次対応者はSentryの時刻と固定種別からFly.ioの該当ログ及びStripeの送信履歴を権限のある画面で照合し、原因解消後に通常操作又は署名付き再送の成功を確認して解決する。通知送信の失敗はFly.ioの固定ログで確認する。

本番の外部送信と秘密値登録は別途承認が必要。承認前は無効を維持し、架空データの到達・メール・失敗時の動作、無料枠とプロセス数、検知遅延、通知が届かない場合の手順を確認してから有効化する。既存の日次Cronは増やさず、日次決済点検との接続も別作業とする。

## バックアップと復元

### 管理方針と確認状況

バックアップの実装、ワークフロー、接続・鍵管理の手順、詳細な実施記録は専用の非公開リポジトリで管理する。[運用資料の管理方針](../operations/README.md)に従い、公開側には方針と結果の要約だけを残す。秘密値・復号鍵・DBデータは非公開側にもコミットしない。

- 追加費用0円、専用の読み取り接続、暗号化保管、復号鍵の別保管、運営者だけの閲覧を維持する。DBの復元履歴を別保管のバックアップと同一視しない。
- 個別承認後、初回と日次用の手動バックアップを保管先から取得し、隔離環境で復元・整合性確認に成功した。本番DBへの書戻しは行っていない。
- 日次取得・状態通知は有効化済み。初回予定の未実行警告は手動補完と実処理の正常通知で自動解決した。起動欠落の内部原因は未特定で、定期起動の成功・継続は未確認。詳細な設定を変えずに再有効化した経緯は [公開用の調査要約](日次バックアップ未実行調査_2026-10-21.md) を参照する。
- 試用終了後の無料プランでの継続、復旧目標の合意・達成、復元後アプリの主要画面の確認は残件。取得・復元処理の一部所要時間を、障害発生からの復旧時間として扱わない。

### 日次運用の確認と停止

1. 非公開リポジトリの実行履歴と暗号化成果物、監視側の本番チェックインを照合する。設定の有効化・手動成功と、予定時刻の自動起動を区別する。
2. 失敗時は取得・保存・通知のどこで止まったかを確認する。通知だけが失敗しても保存済みの暗号文を消さず、秘密値や接続URLをログへ出さない。
3. 未実行警告では、履歴なし・待機・スキップ・処理失敗を区別する。費用条件を確認して既存処理を補完し、成果物と実処理の正常通知による復旧を確認する。通知だけを成功へ書き換えない。
4. 無料枠・容量不足では追加予算を増やさず停止する。意図的な停止は取得処理と監視をそろえ、既存成果物の保持期限を確認する。再開時は費用・復元可能性・通知設定を再確認し、必要な承認を得る。具体的な操作は非公開の運用手順に従う。

### 論理バックアップの手順

1. 対象DB、直接接続、バックアップ用権限、空き容量を確認する。接続情報は権限制限したPG service/passfile等で与え、URLをコマンド引数・共有ログへ埋め込まない。
2. DB、`pg_dump`、`pg_restore` のメジャーバージョンをそろえる。新しいツールで古いDBをdumpできても、古いDBへ復元できるとは限らない。
3. `pg_dump --format=custom --no-owner --no-acl` で全スキーマを取得する。問題だけに絞らず、users、履歴、お気に入り、決済、購入資格、検証資格、Webhook処理済み記録、同期記録も含める。
4. 制限された作業ディレクトリ（0700）・ファイル（0600）と承認済みの暗号化方法を用いる。実行時刻、ツール版、終了コード、暗号化済みファイルのサイズ・ハッシュだけを記録する。終了コード非0や空ファイルを成功扱いしない。
5. 一時名から完了名へ切り替え、保存先で読取り権限と復号可能性を確認する。定期実行後は最終成功時刻も監視する。復元検証前に古い成功分を削除しない。

### 隔離環境への復元

1. 本番・既存開発DBとは別の空DBを作り、接続先を二重に確認する。名前の付け替えだけで本番URLを流用しない。文字コード・ロケール提供方式・照合順序も元DBにそろえる。
2. 外部送信、実Stripeキー、Webhook受信、定期ジョブ、販売を無効にする。本番データを使う場合はアクセス権を限定する。
3. 復号したdumpを `pg_restore --dbname <隔離した新DB名> --exit-on-error --single-transaction --no-owner --no-acl <dump>` で新DBへ戻す。接続先を明示し、既存DBを `--clean` で上書きしない。失敗したDBをアプリへ切り替えない。
4. 全テーブルの件数・内容照合、外部キー・一意制約・CHECK制約、4択と正答1件、選択肢と履歴の対応、お気に入り、支払と資格、返金・異議申立て、Event ID重複防止、検証資格の期限・取消、管理者権限を確認する。
5. 隔離したアプリからログイン・問題・履歴・お気に入りを確認する。復旧対象時刻、検証者、所要時間、失う更新範囲を記録する。本番への切替は運営者の承認後に別作業として行う。

### ローカルの架空データによる復元検証

通常のDocker開発環境を準備した後、リポジトリ直下で実行する。

```sh
bash scripts/restore-drill.sh
```

ローカルにある公式 `postgres:16` イメージからツールだけを取り出す。未取得の場合は先に `docker pull postgres:16` で取得する。既存のバックエンドの一時ディレクトリで使い、通常のアプリ用ツールやDBサーバーを置き換えない。一時DBを新規に2件作り、現行スキーマと架空のユーザー・管理者・問題・4択・履歴・お気に入り・支払・資格・Webhookを投入する。custom dumpからもう一方へ復元し、全テーブルの件数と内容ハッシュ、制約・インデックス・シーケンス、関連を照合する。ダンプ、一時DB、ツールと一時コンテナは終了時に除去する。test環境かつローカルホスト以外では拒否し、既存DBへは投入・復元しない。

出力の `data: synthetic_only` は本番バックアップの検証ではないことを示す。本番の定期バックアップ・復号・復旧目標の達成確認は別途必要である。

## セキュリティ・ログ・応答性能

- Fly.ioのHTTPS転送、NetlifyのTLSとPrivate、会員・有料・管理者のAPI認可を維持する。フロントの認証CookieはproductionでSecure、SameSite=Lax。APIへのBearer送信に使うためHttpOnlyではなく、HTMLを直接挿入しない実装とトークン非出力も維持する。
- Railsログはstdout・既定info・request ID付き。Fly.ioアプリ／組織のログ閲覧権限、保存先・保持期間・外部転送、過去の漏えいの有無は管理画面で別途確認する。現在のフィルターが過去ログも消したとは扱わない。
- 登録・ログイン・回答・Checkoutの共有レート制限と追加テーブルの本番反映を確認した。PostgreSQLの共有カウンターを使い、同時接続でも原子的に加算する。IP・ユーザーIDは秘密鍵付きハッシュに変換し、生の識別情報をカウンターへ保存しない。PrivateはAPIの保護やこの制限の代替ではない。少数のログイン成功確認を、共有IPの多数利用や本番の上限試験が完了したものと扱わない。
- 初期値はログイン30回/5分/IP、登録10回/15分/IP、回答120回/分/IP、Checkout20回/5分/IPかつ10回/5分/ユーザー。失敗・成功とも数え、429とRetry-Afterを返す。失効行は次の制限対象リクエストで最大100件ずつ削除する。Webhookと公開GETは対象外。学校等の共有IPや実利用の影響は公開前に確認し、必要なら初期値を調整する。固定窓の境界や分散した大量通信を完全に防ぐものではない。
- リリース時は `api_rate_limit_buckets` の追加マイグレーションを先に完了させる。既存テーブル・問題データは変更しない。専用バックアップロールの既定のSELECT権限が新表にも適用されたことを、取得前にメタデータで確認する。バックアップはpublic全表を対象とするため、この表も暗号化して保管される。保存先障害では対象操作を503・Retry-After:60で停止するため、503が続く場合はDB接続・マイグレーション・権限を確認する。テーブルを削除して迂回しない。
- 応答の初期基準はウォーム時の問題取得・回答・履歴3秒以内、スリープ復帰時90秒以内、表示中の操作を妨げるエラーなし。スリープの遅延は許容する。少数回の測定をp95や全利用者の保証とせず、自然停止後と通常時を区別する。本番を強制停止して測定しない。

## デプロイと障害復旧

1. 変更範囲とテスト結果を確認する。DB変更があれば互換性と復元可能性も確認し、mainへpushする。自動リリースの重複実行を避ける。
2. Fly.ioの全マシンが自然停止中の場合、リリース開始前に通常のhealthアクセスで起動を確認する。リリース待機中は担当者が一時的に通常アクセスを確認し、終わったら終了する。永久ポーリングやmin_machinesの引上げへ無断で変更しない。
3. リリースがlease保持中に502になっても、進行中のleaseを強制解除したり並行再デプロイしたりしない。リリースの終了・失敗とlease解放を確認してから通常アクセスで復帰を確認する。現在はseedを実行しないため、長時間待つ場合はDB準備・接続・ロック待ちを調べる。
4. APIのhealth、公開問題、未認証の保護API、CORS許可・拒否を確認する。必要な会員操作は承認済みの確認アカウントだけで行う。
5. NetlifyのPublishedコミットとPrivateを確認する。資料だけのコミットがCanceledの場合は、実際の配信コードとの差分とキャンセル理由を区別して記録する。
6. フロント障害はNetlifyの直前の保護済み成功デプロイへ戻す。DB復元やRailsの再デプロイを同時に行わない。自動公開による再上書きにも注意する。
7. API障害ではリリース状態・health・設定不足・DB疎通を確認する。直前のAPI版へ戻す場合もマイグレーション互換性を確認し、安易にDBを巻き戻さない。
8. 旧Vercelへの切戻しは、保護済み成功版の特定、アクセス保護とCORSの個別再許可を確認してから判断する。Git連携を自動で復活させない。旧版の削除期限は未決定のため削除しない。

## 問題データの編集と新規環境への移送

2026年10月21日のユーザー承認により、実行用seedとデプロイ時の問題同期を廃止する。既存DBを正本とし、訂正・非公開化・削除は管理画面から行う。`db:seed` は何もしない。通常のデプロイで問題が増減・上書きされることはない。

### 問題だけの書き出し

ローカルのコンテナ内で、存在しない出力ファイルを明示する。`tmp/` はGit管理外であり、出力は0600となる。親ディレクトリの閲覧権限も制限し、共有先・保存期間を決める。出力パスはコンテナ内のパスである。

```sh
docker compose exec -T backend bin/rails questions:export OUTPUT=tmp/questions-export.json
```

- DBはrepeatable-read・read-only transactionで読み、問題・選択肢・公開状態だけを出力する。件数・形式バージョン・SHA-256を記録するが、本文を標準出力へ出さない。
- 同じファイルへの上書きは拒否する。SHA-256は転送・破損の照合用であり、送信元の真正性や承認の代用ではない。信頼した経路でファイルと照合値を受け取る。
- ユーザー、認証情報、決済、履歴、お気に入り、レコードIDを含まない。利用者データやIDを保持する復旧には、承認済みの完全DBバックアップを使用する。
- 本番の取得・バックアップには非公開運用側の承認済み手順を使う。本節を根拠に本番DBを無断で取得・書き戻ししたり、新しい保管・通知先を追加したりしない。

### 新しい空環境への明示取込み

問題と選択肢が両方空の環境だけが対象。接続先を確認し、承認済みアーカイブをその環境へ安全に配置した後に実行する。以下はローカル開発環境用の例であり、既存ローカルDBへは取込みできない。空にするための削除は行わない。

```sh
docker compose exec -T backend bin/rails questions:import INPUT=tmp/questions-export.json CONFIRM=IMPORT_INTO_EMPTY_DATABASE
```

- 形式・件数・チェックサム・重複番号・4択・正答1件を検査し、公開問題には本文・出典・空欄等とセットの問1〜20登録検査も適用する。公開・非公開・下書きを保持する。
- 明示確認がない場合や、既存問題・選択肢がある場合は拒否する。途中で失敗した場合は全件ロールバックする。既存DBへのmerge・上書き同期は提供しない。
- 取込み後は出力件数と元の照合値を確認し、公開構成を `frontend/app/utils/examCatalog.ts` と照合する。管理者ログインや会員・決済設定は別途準備する。

### seed廃止版を本番へ出す際の確認

1. 最終承認内容が本番に反映されていることを読み取りで確認し、利用可能な暗号化バックアップと復元手順を確認する。ローカルの一致だけで本番一致としない。過去に成功した完全バックアップの記録と、今回の最新状態の確認は区別する。
2. 新版のrelease commandが `db:prepare` だけであることと、`test/` が本番イメージへ入らないことを確認する。未初期化DBの `db:prepare` と手動seedでも0問のままになる。
3. 新版デプロイ後、問題・公開状態と関連データの件数・全属性ハッシュ及び管理APIの通常動作を確認する。管理者の実データを検証のために書き換えない。
4. `question_seed_states` は今回は削除しない。release中の旧版や切戻し候補が表を参照するためである。旧版の稼働・切戻し期間終了後に、別途承認したマイグレーションで撤去する。
5. 旧版へ切り戻すと自動seed同期が復活し得る。切戻し時もrelease commandを明示確認し、管理画面で編集済みのDBへ旧seedを再投入しない。

原典fixture・承認記録・旧問題カタログはテスト専用として保存する。`test/fixtures/approved_question_catalog/` は凍結回帰資料であり、新規環境への投入元ではない。通常の訂正に合わせて過去の承認ハッシュを書き換えない。

### 廃止版のローカル検証（2026年10月21日）

- 旧50セットと固定比較値の51ファイルは移設前コミット `3aa6f15` と全バイト一致。承認snapshot・原典fixture・過去の固定ハッシュは変更していない。
- 既存ローカルの全1,000問・4,000選択肢・公開状態は承認カタログと一致。DB準備と手動seed2回の後も、問題・選択肢・履歴・お気に入り・ユーザー・決済・資格・Webhook記録の9モデルで全属性ハッシュが不変。アプリをeager loadしても旧同期クラス・旧状態モデル・旧payload変換は読み込まれなかった。
- 検証前に権限0600・専用ディレクトリ0700でローカル一時バックアップを取得した。検証終了後にも9モデルの不変性を再確認し、個人情報を含むその一時コピーだけを削除した。元DBは保持されており、本番の暗号化バックアップや非公開運用設定は変更していない。
- 別名で新規作成した隔離ローカルDBでは、初回 `db:prepare` と手動 `db:seed` 2回の後も問題・選択肢は0件。既存ローカルから読み取り専用で書き出したアーカイブを取り込み、1,000問・4,000選択肢を復元できた。再書き出しの全payload及びチェックサムが元と完全一致した。一時DBと復元用作業フォルダは検証後に削除済み。
- バックエンド全体492件・89,924検証を1回実行し、旧テストの準備に依存する5件の不一致を検出した。2件は廃止した削除tombstoneを過去の検査用設定として明示し、3件は大量回答の検査が本物の回数制限へ達しないよう隔離テストDBの一時カウンターを問題ごとに初期化した。実運用の制限値・認可・全選択肢判定・回答前秘匿の検査は変更していない。
- 修正した5件は再実行で24,842検証すべて成功。保存・削除・移送・既存同期行を無視する契約・回数制限の重点35件も290検証すべて成功した。変更対象の再検証で不一致は解消しており、全体492件の2回目の実行は行っていない。
- この確認はローカル限定。本番の最終内容照合・デプロイは実施しておらず、コミット・pushも別途の承認対象。完全DBバックアップの既存の暗号化・隔離復元記録を、今回の本番最新状態を確認した証拠とは扱わない。
