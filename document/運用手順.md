## Nuxt/Nitro移行後の入口（2026年10月24日）

現在の実装は `frontend/server/`、DB操作はPrisma、認証はBetter Auth、マイグレーションはPrisma Migrateを使用する。旧Railsの実施記録は当時の確認結果であり、新実装の本番検証完了を意味しない。移行の進捗・実測結果は [テンプレート移行記録](テンプレート移行_2026-10-24.md) へ記録する。

- CLIは `frontend/` で `npm run operations -- <操作名>`、Compose内では `docker compose exec -T frontend npm run operations -- <操作名>` を使用する。入力の秘密値は環境へ安全に渡し、コマンド引数・共有ログへ値を残さない。
- 通常のDB準備は `npm run db:migrate`。起動・リリース・`npm run db:seed` では問題を投入しない。`content/questions.json` は合成テスト専用40問であり、本番に取り込まない。
- 通常のComposeは `frontend` と `nuxt-db` の2サービスだけとし、新DBは `nuxt_postgres_data` に保存する。旧DBは同じプロジェクトのprofileではなく、`docker-compose.legacy.yml` に分離する。旧コンテナが通常のDocker Desktopグループに残っている場合は、対象が停止済みであることを確認してコンテナだけを `docker rm` し、元の `tqce-info-practice_postgres_data` と旧依存volumeを保持する。旧DBの必要時だけ `docker compose -p tqce-info-practice-legacy -f docker-compose.legacy.yml up -d db`、使用後は同じ `-p` / `-f` で `down` する。`-p` を省略せず、通常設定に旧設定を重ねない。旧volumeはexternal参照で、名前が異なる場合だけ `LEGACY_POSTGRES_VOLUME` に既存名を設定する。`docker compose down -v` や旧volumeの削除をしない。
- 今回は問題・選択肢の全列とID・マイクロ秒日時を保全し、ユーザー・履歴等を新DBへ移さない承認を受けている。旧DBと完全バックアップは切戻し用に保持する。新ユーザーを既存のStripe metadataのユーザーと誤って関連付けないことも切替時に確認する。
- 作業時のバックアップはGit管理外の `operations/private/template-migration-20261024/` に限定し、ファイル0600・親0700とする。問題本文・正答・個人情報・接続文字列を公開資料やイメージへ同梱しない。
- 旧環境のバックアップ設定を、新DBに自動追従したものとみなさない。新DBの接続先・バックアップ専用ロール・対象表・隔離復元を確認する。追加の通知・販売開始・Private解除は行わない。
- 重い検証・ビルドはCPU・メモリを制限して一つずつ実行する。Netlifyはローカル検証とFly.io切替完了後の最終1回だけ反映する。

- 公開前はNetlifyの本番・プレビューをPrivateにする。Fly.ioのAPIは別の公開口であり、CORSだけでアクセスを制限できるとは扱わない。
- 販売開始の承認と下記の確認が完了するまで `PAID_MEMBERSHIP_ENABLED` を有効にしない。
- 2026年10月21日に問題完成・seed廃止が承認された。通常リリースは `npm run db:migrate` のみとし、本番DBを正本に管理画面で編集する。15分のrelease timeoutはDB準備の上限として維持し、問題の自動投入・同期を追加し直さない。
- デプロイ、バックアップ確認、決済照合だけを理由に、本番問題・会員・履歴を削除しない。

## 確定した運用方針（2026年10月21日）

所有者が次の方針と、変更の一括保存・販売停止での反映・実環境確認の順序を承認した。方針の承認を、その実装・本番動作・目標達成の証拠とは扱わない。販売開始とPrivate解除は含まない。

同日の追加指示により、Sentryの画面確認と新しい通知の有効化は今回は見送る。既存のバックアップ通知設定は維持し、APIの外部通知と日次決済点検の新規有効化は未完のまま残す。外部サービスの障害が原因かどうかは断定しない。

| 項目 | 確定した方針 |
| --- | --- |
| バックアップ | 日次取得を維持し、データ損失は1日分以内（RPO 24時間）、復旧は24時間以内（RTO 24時間）を目標とする。実際の取得間隔と隔離復元で達成可否を確認する |
| 障害通知 | 既存のメール通知先を使い、利用時のAPI障害と日次点検で検知する。利用がない時間帯の完全停止の即時検知や、無条件の24時間即応は対象にしない |
| ログ | 運営者だけが閲覧する方針とし、既存の標準ログを使用する。追加の長期保管・外部転送は設けない。実際の権限棚卸しと過去分の点検は別に確認する |
| 費用・反映 | 追加費用0円を維持する。フロント変更をまとめて1回反映し、バックエンドと非公開運用側も差分確認後に反映する。販売OFF・Privateを維持する |

日次の実行遅延、無料枠・保管容量の不足、取得失敗で最終正常バックアップから24時間を超える場合は目標未達として調査する。日次設定そのものを、24時間以内の取得保証とは表示しない。復旧は運営者が障害を認識して復旧作業を開始する判断から、復号・復元・主要操作確認までを計測する。鍵・接続権限・保管先へ到達できない時間も除外して達成済みとはしない。

## 読み取り専用の点検

`frontend/` で `npm run operations -- operations:audit` を実行する。本番ではFly.ioの対象アプリへ接続してから実行する。追加の公開APIやフロントエンドのポーリングは設けない。

出力は設定不足の項目名、販売の有効・無効、集計件数、警告名と確認日時だけとする。メールアドレス、ユーザーID、Stripe ID、DB接続文字列、秘密値は出さない。DBトランザクションは読み取り専用で、Stripeへの通信や決済・資格の変更は行わない。

| 項目 | 確認内容 |
| --- | --- |
| `payment_configuration_issues` | 必須設定の不足、キーと実行モードの不一致、戻り先URLの不正、本番のテストモード |
| `stale_pending_checkouts` | 作成から24時間以上経過した未完了決済。障害と断定せず、Stripe上のSessionと照合する |
| `refund_failures_last_day` | 過去24時間に返金失敗を受信した決済 |
| `disputed_payments` | 異議申立て状態の決済。解決済みでも手動確認待ちを含む |
| `active_memberships_with_revoked_payment` | pending・expired・refunded・disputedの決済を根拠に有効になっている資格 |
| `processed_webhooks_last_day` | 過去24時間の処理済みWebhook件数。0件だけでは障害と判断しない |

点検結果は警告名、設定不足名、集計件数で確認する。コマンドの実行成功だけを警告なしとみなさず、返された警告を点検する。販売を止めている期間の設定不足は、障害ではなく販売準備の残件として扱う。定期実行と通知は別途設定が必要で、このコマンドを追加しただけでは有効にならない。

## Stripeの販売開始条件

1. Stripeのテスト環境で、購入成功、未完了・取消、同じWebhookの再送、重複購入防止、全額返金、異議申立てを確認する。ローカルの模擬応答テストと実Stripeの試験は分けて記録する。
2. 本番のProduct・Priceが日本円500円・一回払い・有効であることを確認する。`STRIPE_SECRET_KEY`、Price、Webhook送信先・署名シークレットを同じ本番モードにそろえ、`STRIPE_LIVEMODE=true` とする。
3. `FRONTEND_URL=https://johokyonin-lab.netlify.app` とする。成功時は `/premium/complete`、取消時は `/premium?canceled=1` に戻る。HTTPSのオリジンだけを指定し、認証情報、パス、クエリ、フラグメントを入れない。ローカルのHTTPはlocalhost/127.0.0.1だけを許可する。本番ドメインを変更するときは `CORS_ORIGINS` も同じオリジンへ切り替え、旧オリジンの拒否と新オリジンの疎通を確認する。
4. Webhook送信先は `https://tqce-info-practice.fly.dev/api/v1/webhooks/stripe` とし、README記載の7イベントを登録する。署名不正400、正しい通知200、再送時の非重複を確認する。
5. 販売者名、責任者、住所、電話番号、連絡先、提供内容・時期、返金条件、利用規約とプライバシーポリシーを運営者が最終確認する。仮の連絡先や架空の事業者情報では開始しない。
6. バックアップ・復元、監視通知、HTTPS・認可、応答性能の公開前残件を解消する。運営者が販売開始を承認した後にだけ販売フラグを有効にする。
7. 有効化後に公開販売設定と導線を確認する。本番の実決済が必要なら金額・実行者・返金の扱いを先に承認し、検証用資格で代用したものを購入試験済みとしない。

販売設定に問題があればフラグを無効へ戻す。既存購入者の資格を一括で削除したり、支払済みの記録を手動作成したりしない。キーや事業者情報の値はIssue・コマンド履歴・ログへ貼らない。

### 販売者と返金方針の確認状況（2026年10月21日）

- 販売者・運営責任者は所有者本人とし、氏名の申告を受けた。実値は公開販売設定から表示する方式を維持し、公開リポジトリ・Issueへ追記しない。Fly.ioの環境設定は変更していない。公開APIの請求時開示対応はローカル準備であり、本番へは未反映。
- 所有者の意向は任意の返金を受け付けないこと。既存の規約・販売案内・特商法表記にある、提供開始後の利用者都合の返金は原則不可という説明と、重複決済・提供不能等の例外を維持する。法令上の解除・返金等まで一律に排除する「理由を問わず一切返金不可」へ書き換えない。販売形態に即した最終文面の確認は残す。
- 法令上必要な対応や実際のStripeの返金・異議申立ては発生し得るため、Webhook処理・記録・資格失効・返金失敗時の整合処理を削除しない。購入者向けの任意返金受付機能は追加しない。
- 購入者向け問い合わせ先は所有者指定のメールアドレスで確定した。監視用に指定したアドレスとは別に扱う。所在地・電話番号は下記の請求時開示方式とし、本番設定への反映は別途承認を得る。
- 根拠として、[消費者庁の消費者契約法第8条の2解説](https://www.caa.go.jp/policies/policy/consumer_system/consumer_contract_act/annotations/assets/consumer_system_cms203_230915_14.pdf)で、債務不履行による消費者の解除権を放棄させる条項等が無効とされることを確認した。今回の確認は、個別の販売条件全体の適法性を保証するものではない。

### 所在地・電話番号の請求時開示

2026年10月21日、所有者から、私用の所在地・電話番号を常時公開せず、問い合わせメールで請求を受けて遅滞なく実情報を回答する方針と、購入前にも対応可能との確認を受けた。実値はこの資料へ記録せず、アプリで取得・保存する機能も追加しない。

- [消費者庁の通信販売の案内](https://www.no-trouble.caa.go.jp/what/mailorder/)の「広告の表示事項を省略できる場合」を確認した。省略の案内を表示するだけでなく、購入の意思決定に先立って十分な時間的余裕をもって実際に開示できる措置が必要となる。購入後だけの回答、架空の住所・番号、正当な請求の一律拒否で代替しない。
- `SELLER_CONTACT_DISCLOSURE_MODE=on_request` とし、体制確認後だけ `SELLER_CONTACT_DISCLOSURE_READY=true` を設定する。いずれもバックエンドの設定であり、販売開始フラグとは独立している。今回、本番設定は変更していない。
- 氏名・責任者・問い合わせ先は既存の販売者設定から表示する。住所・電話番号の実値を `NUXT_PUBLIC_SELLER_ADDRESS`・`NUXT_PUBLIC_SELLER_PHONE` やNetlifyへ追加しない。古い値が残っていても、この方式のAPIは実値を返さない。既存設定の削除も別途承認なしでは行わない。
- `/commercial-disclosure` の所在地・電話番号欄に「請求があった場合に遅滞なく開示します」と表示し、問い合わせメールによる請求方法、購入前の電子メール回答、無料での開示を説明する。
- 所有者が指定メールの受信と返信を運用する。購入・会員登録・開示費用の支払を回答の条件にしない。実際の住所・電話番号と個別の請求・回答内容を公開Issueや共有ログへ残さない。
- 確認済みの氏名・問い合わせ先・開示方式の本番反映用設定案は、Git管理外のローカルファイルに限定して保管する。自動では読み込まず、設定の適用は別途承認後に販売OFFを保ったまま行う。この確認だけでStripe側の登録要件や販売全体の適法性まで確認済みとはしない。

## Webhook・決済の障害対応

| 状況 | 確認と対応 |
| --- | --- |
| Checkoutで502 | Fly.ioの時刻・request IDと `Stripe Checkout Session creation failed` を確認。Stripe側の障害・キーとモード・通信状態を確認する。連打で別決済を作らない |
| Webhookで400 | 署名、対象endpoint、実行モード、金額・通貨・metadataの照合を確認。署名検証を外して通さない |
| Webhookで500 | `Stripe webhook processing failed` と例外クラスを確認。Stripe Dashboardの対象イベントと送信履歴を照合する。DB更新はロールバックされるため原因を解消して再送する |
| 支払済みなのに資格反映待ち | Stripe上のSession・PaymentIntent・対象ユーザーの対応を権限のある画面で確認する。対象の署名済みイベントを再送し、同じEvent IDで重複がないことを確認する |
| 非同期の返金失敗 | 失敗理由と受信日時に加え、Stripeの現在の成立済み返金額と決済状態を照合する。同じ購入の返金だけによる資格失効は、全額返金・紛争が残っていなければ自動で元へ戻る。紛争や別購入の資格は自動で戻さない。照合通信が失敗した場合は処理済みとせず再送する |
| 返金・異議申立て | 決済とStripeの状態を照合する。全額返金・異議申立てで資格を停止する仕様を維持する。異議申立て終了後の資格再開は自動では行わない |
| 24時間超のpending | Sessionを取得して未完了・expired・completeを確認する。既存の `PendingCheckoutExpirer` の仕様に従う。支払済みを単にexpiredへ書き換えない |

再送はStripe Dashboardの対象イベントから同じ送信先へ行う。本文をコピーして署名を偽造したり、DBへ有料資格だけを書き込んだりしない。再処理後は決済1件・購入資格1件、処理済みEvent IDの重複なしを確認する。テスト環境で先に実施し、本番への金銭操作やデータ修正は個別に承認する。

### 監視の現状と未設定事項

担当はリポジトリ所有者を一次窓口とする。追加費用0円・メール通知を前提とし、通知先の実値は公開資料へ記載しない。

- バックアップの日次状態通知は個別承認後に有効化し、手動実行の正常通知と、架空データによる障害・復旧メールの受信を確認済み。定期起動の継続と試用終了後の無料プランでの継続は別途確認する。
- APIの障害通知は実装の本番反映まで確認したが、外部送信は無効。本番有効化・到達試験・許容する検知遅延は残件。既存のバックアップ通知の承認を流用しない。
- API healthの定期ポーリングやFly.ioの常時起動は設定しない。利用時のエラー通知と、利用がない時間帯の完全停止の即時検知は区別する。
- 決済集計の日次点検はローカル接続準備まで完了し、本番反映・有効化は残件。既に確認済みの異議申立てを毎回新規障害として通知しないための運用も、有効化前に確定する。
- 日次処理とAPIの通知は分け、利用者情報・接続情報・リクエスト本文を送らない。詳細設定は専用の非公開リポジトリ、公開可能な結果は [公開前運用確認](公開前運用確認_2026-10-20.md) で管理する。

### API障害通知（公式SDK・外部送信は初期無効）

`frontend/server/core/notifications.ts` でSentry公式Node SDKの独立クライアントを使用する。旧Railsの `ApiErrorNotifier` と独自送信実装は現行APIで使用しない。旧実装の2026年10月21日の実環境確認を、新実装の実Sentry到達確認として扱わない。

| 設定 | 初期値・用途 |
| --- | --- |
| `ERROR_NOTIFICATIONS_ENABLED` | `false`。文字列 `true` の場合だけ送信 |
| `SENTRY_ERROR_DSN` | バックエンドのSecretにだけ設定。許可したSentry HTTPS取り込み先 |
| `ERROR_NOTIFICATION_ENVIRONMENT` | `verification` 又は `production` |

- 対象はAPIで扱ったHTTP 5xx。一般API・Stripe API接続・Webhook処理の固定カテゴリで、販売停止・Webhook未設定として予定どおり返す503を除く。レート制限保存先の障害等は除外しない。
- 自動integration、リクエスト・利用者情報、Cookie、HTTP本文、DBクエリ、スタック、breadcrumb、tracing、session/log/metric送信は無効。固定メッセージ・時刻・ランダムID・環境・重大度・固定カテゴリタグだけを送る。SDKの最終イベントフックでも許可項目へ作り直す。
- 同じ種類・環境は1プロセス1時間に1回まで。失敗した送信も同じ窓では再送しない。再起動・複数マシンにより合計は増えるため、Sentry全体の厳密な上限ではない。
- 絶対期限1秒、リダイレクトなし。通知失敗で元のAPI応答やWebhook再送の意味を変えない。実Sentryの到達・通知メール・無料枠・検知遅延は、送信有効化を別途承認する前に確認する。
- 利用がない時間帯の停止・起動前・ネットワーク断の即時検知は行わない。healthの永久ポーリングや新しいCronを追加しない。

### 日次決済点検（ローカル準備のみ・未反映）

- 専用の非公開リポジトリに、既存のバックアップ用読み取り権限で決済状態の件数だけを点検する処理と、既存の日次処理への接続を準備した。公開API・新しいCron・管理用トークンは追加しない。
- Railsの `OperationsSnapshot` と同じ5種類の件数を、UTC・読み取り専用トランザクション・短い実行時間制限の下で取得する。バックアップと同じ事前の接続先・権限検査を通し、架空DBで書換えがないことも検証した。Rails側の販売設定点検やStripeとの実取引照合の代替ではない。
- 初期状態は無効とし、別途承認した有効化設定がある場合だけ実行する。承認なしでは従来の日次処理を維持する。警告や処理失敗を正常通知へ変えず、保存済みの暗号化バックアップは消さない。
- 外部へ送るのは既存の実行状態通知だけで、件数・警告の詳細・利用者情報を付加しない。確認済みの異議申立ての扱い、同じ異常が続く場合の通知、無料枠、実環境の到達試験を有効化前に確認する。
- 現時点ではローカル試験のみ。非公開リポジトリへのpush、実行設定の変更、本番DBへの追加の読み取り、実際の通知は行っていない。

## バックアップと復元

### 管理方針と確認状況

バックアップの実装、ワークフロー、接続・鍵管理の手順、詳細な実施記録は専用の非公開リポジトリで管理する。[運用資料の管理方針](../operations/README.md)に従い、公開側には方針と結果の要約だけを残す。秘密値・復号鍵・DBデータは非公開側にもコミットしない。

- 追加費用0円、専用の読み取り接続、暗号化保管、復号鍵の別保管、運営者だけの閲覧を維持する。DBの復元履歴を別保管のバックアップと同一視しない。
- 個別承認後、初回と日次用の手動バックアップを保管先から取得し、隔離環境で復元・整合性確認に成功した。本番DBへの書戻しは行っていない。
- 日次取得・状態通知は有効化済み。初回予定の未実行警告は手動補完と実処理の正常通知で自動解決した。起動欠落の内部原因は未特定で、定期起動の成功・継続は未確認。詳細な設定を変えずに再有効化した経緯は [公開用の調査要約](日次バックアップ未実行調査_2026-10-21.md) を参照する。
- 試用終了後の無料プランでの継続、復旧目標の合意・達成、復元後アプリの主要画面の確認は残件。取得・復元処理の一部所要時間を、障害発生からの復旧時間として扱わない。

### 日次運用の確認と停止

1. 非公開リポジトリの実行履歴と暗号化成果物、監視側の本番チェックインを照合する。設定の有効化・手動成功と、予定時刻の自動起動を区別する。
2. 失敗時は取得・保存・通知のどこで止まったかを確認する。通知だけが失敗しても保存済みの暗号文を消さず、秘密値や接続URLをログへ出さない。
3. 未実行警告では、履歴なし・待機・スキップ・処理失敗を区別する。費用条件を確認して既存処理を補完し、成果物と実処理の正常通知による復旧を確認する。通知だけを成功へ書き換えない。
4. 無料枠・容量不足では追加予算を増やさず停止する。意図的な停止は取得処理と監視をそろえ、既存成果物の保持期限を確認する。再開時は費用・復元可能性・通知設定を再確認し、必要な承認を得る。具体的な操作は非公開の運用手順に従う。

### 論理バックアップの手順

1. 対象DB、直接接続、バックアップ用権限、空き容量を確認する。接続情報は権限制限したPG service/passfile等で与え、URLをコマンド引数・共有ログへ埋め込まない。
2. DB、`pg_dump`、`pg_restore` のメジャーバージョンをそろえる。新しいツールで古いDBをdumpできても、古いDBへ復元できるとは限らない。
3. `pg_dump --format=custom --no-owner --no-acl` で全スキーマを取得する。問題だけに絞らず、users、Better Authの認証・セッション表、履歴、お気に入り、決済、購入資格、検証資格、Webhook処理済み記録、マイグレーション履歴も含める。旧DBの完全バックアップには旧同期記録も含まれる。
4. 制限された作業ディレクトリ（0700）・ファイル（0600）と承認済みの暗号化方法を用いる。実行時刻、ツール版、終了コード、暗号化済みファイルのサイズ・ハッシュだけを記録する。終了コード非0や空ファイルを成功扱いしない。
5. 一時名から完了名へ切り替え、保存先で読取り権限と復号可能性を確認する。定期実行後は最終成功時刻も監視する。復元検証前に古い成功分を削除しない。

### 隔離環境への復元

1. 本番・既存開発DBとは別の空DBを作り、接続先を二重に確認する。名前の付け替えだけで本番URLを流用しない。文字コード・ロケール提供方式・照合順序も元DBにそろえる。
2. 外部送信、実Stripeキー、Webhook受信、定期ジョブ、販売を無効にする。本番データを使う場合はアクセス権を限定する。
3. 復号したdumpを `pg_restore --dbname <隔離した新DB名> --exit-on-error --single-transaction --no-owner --no-acl <dump>` で新DBへ戻す。接続先を明示し、既存DBを `--clean` で上書きしない。失敗したDBをアプリへ切り替えない。
4. 全テーブルの件数・内容照合、外部キー・一意制約・CHECK制約、4択と正答1件、選択肢と履歴の対応、お気に入り、支払と資格、返金・異議申立て、Event ID重複防止、検証資格の期限・取消、管理者権限を確認する。
5. 隔離したアプリからログイン・問題・履歴・お気に入りを確認する。復旧対象時刻、検証者、所要時間、失う更新範囲を記録する。本番への切替は運営者の承認後に別作業として行う。

### ローカルの架空データによる復元検証

通常のDocker開発環境を準備した後、リポジトリ直下で実行する。

```sh
bash scripts/restore-drill.sh
```

起動済みの `frontend` コンテナに同梱したPostgreSQL 16のツールとNode CLI `operations:restore_drill` を使う。旧Railsやツール取り出し用コンテナは使用しない。一時DBを新規に2件作り、現行スキーマと架空のユーザー・管理者・問題・4択・履歴・お気に入り・支払・資格・Webhookを投入する。custom dumpからもう一方へ復元し、全テーブルの件数と内容ハッシュ、制約・インデックス・シーケンス、関連を照合する。ダンプと一時DBは終了時に除去する。test環境かつローカルホスト以外では拒否し、既存DBへは投入・復元しない。スクリプトはDB接続URLの継承を外し、Docker内の `nuxt-db` と販売OFF・通知OFFを明示する。関数を直接呼ぶ場合も、販売フラグ又は外部通知が有効ならDB作成前に拒否する。

旧Rails版では復元先の同じアプリへプロセス内のAPI要求を送り、health、販売停止、一般会員ログイン、本人情報・プレミアム範囲の問題・履歴・お気に入りの取得、一般会員と未ログインの管理API拒否、管理者ログインと問題一覧の計11項目を確認する。HTTPサーバーは新たに公開せず、Stripe・Sentryへ送信しない。パスワードとアクセストークンはプロセス内だけで使い、出力しない。確認後、通常の回数制限カウンターを除く全テーブルの内容ハッシュが不変であることも照合する。

出力の `data: synthetic_only` は本番バックアップの検証ではないことを示す。`application_checks` は復元先で成功したAPI確認の数で、画面の目視確認ではない。経過秒数は架空データを用いた一部の処理時間であり、実データの復旧目標の達成時間ではない。本番の定期バックアップ・復号・復元後操作・復旧目標の達成確認は別途必要である。

## セキュリティ・ログ・応答性能

- Fly.ioのHTTPS転送、NetlifyのTLSとPrivate、会員・有料・管理者のAPI認可を維持する。フロントの認証CookieはHttpOnly・SameSite=Lax、本番はSecureとする。Better Authで管理し、ブラウザのJavaScriptから読み出さない。任意のHTMLを挿入せず、秘密値を出力しない。
- Node/Nitroログはstdoutで管理し、固定した障害分類とHTTP状態を記録する。Fly.ioアプリ／組織のログ閲覧権限、保存先・保持期間・外部転送、過去の漏えいの有無は管理画面で別途確認する。現在のフィルターが過去ログも消したとは扱わない。
- 登録・ログイン・回答・Checkoutの共有レート制限と追加テーブルの本番反映を確認した。PostgreSQLの共有カウンターを使い、同時接続でも原子的に加算する。IP・ユーザーIDは秘密鍵付きハッシュに変換し、生の識別情報をカウンターへ保存しない。PrivateはAPIの保護やこの制限の代替ではない。少数のログイン成功確認を、共有IPの多数利用や本番の上限試験が完了したものと扱わない。
- 初期値はログイン30回/5分/IP、登録10回/15分/IP、回答120回/分/IP、Checkout20回/5分/IPかつ10回/5分/ユーザー。失敗・成功とも数え、429とRetry-Afterを返す。失効行は次の制限対象リクエストで最大100件ずつ削除する。Webhookと公開GETは対象外。個人学習中心・一斉利用を想定しない方針を所有者が確認したため初期値を維持し、実利用で支障が見られた場合に見直す。固定窓の境界や分散した大量通信を完全に防ぐものではない。
- リリース時は `api_rate_limit_buckets` の追加マイグレーションを先に完了させる。既存テーブル・問題データは変更しない。専用バックアップロールの既定のSELECT権限が新表にも適用されたことを、取得前にメタデータで確認する。バックアップはpublic全表を対象とするため、この表も暗号化して保管される。保存先障害では対象操作を503・Retry-After:60で停止するため、503が続く場合はDB接続・マイグレーション・権限を確認する。テーブルを削除して迂回しない。
- 応答の初期基準はウォーム時の問題取得・回答・履歴3秒以内、スリープ復帰時90秒以内、表示中の操作を妨げるエラーなし。スリープの遅延は許容する。少数回の測定をp95や全利用者の保証とせず、自然停止後と通常時を区別する。本番を強制停止して測定しない。

2026年10月21日のローカル追加試験では、同じ共有IPから10人がログインし、同じ1分の窓で各12回答・合計120回答を保存できること、121件目は履歴を増やさず429となること、他のIP・次の時間窓では再開できることを確認した。履歴が本人以外へ混ざらないことも検査した。120回は1人当たりではなくIP全体の上限であり、10人が各20回答を同じ1分内に行う200回の利用には足りない。上限は今回変更していない。その後、所有者は一斉利用を想定しないと確認した。共有回線そのものは禁止せず、個人学習を対象に通常操作と応答を確認する。本番の性能確認は引き続き未完了であり、この逐次試験を本番の同時負荷試験とは扱わない。

### Cookieの実ブラウザ確認

1. Privateを維持した本番サイトへ承認済みの確認アカウントでログインする。
2. 開発者ツールのCookiesで `tqce-info-practice-auth` を接頭辞に含むBetter AuthのセッションCookieを確認する。Secure環境では `__Secure-` が付く。Value列を隠し、値をコピー・撮影・共有しない。
3. HttpOnly、Secure、SameSite=Lax、Path=/、Domain指定なしで本番ホストのみ、有効期間おおむね24時間を確認する。JavaScriptから読取り・Bearerヘッダーへ転記する処理は設けない。
4. 画面更新と一般・管理画面の共有セッション、ログアウト後のCookie削除・保護画面の拒否を確認する。販売ONや実決済は不要。

旧 `tqce-access-token` の2026年10月21日の所有者による確認は旧方式の記録である。新Cookieの実ブラウザ確認結果は移行記録に別途残す。

### ログの保持・閲覧方針（所有者承認済み・実環境の棚卸しは別途）

- Node/NitroのstdoutをFly.ioの標準機能で確認し、追加のログ保管サービスや外部転送は設けない。2026年10月21日に確認した[公式資料](https://docs.fly.io/monitoring/search-logs)では、検索可能なログは7日保持・ベータ中無料とされている。独自の長期保管や恒久的な無料提供を保証するものではなく、公開前及び提供条件変更時に再確認する。
- [Fly.ioの公式権限資料](https://docs.fly.io/security/org-roles-permissions)ではMemberとAdminの双方がログを閲覧できる。共有・委任・既存トークンを含めて棚卸しし、確認できた範囲だけで他の閲覧経路がないと判断しない。棚卸しは未完で、今回アクセス権は変更していない。
- 氏名・メールの旧Railsフィルターは当時の確認記録であり、新Node実装の保証には使わない。現行コードは生のリクエストや例外を出さず、固定した障害分類・状態だけをログへ記録する。本番反映前のログや、IP・時刻・パスなどフィルター対象外の記録は別途扱う。
- 障害の確認には日時とrequest IDを優先し、生ログをIssue・公開資料・チャットへ貼らない。今回の点検でも生ログのローカル保存や外部転送は行わない。
- 過去分は標準の保持範囲で、フィルター反映前後の認証・決済操作に秘密情報の出力がないかを必要最小限で確認する。生ログの取得コピーや新しい長期保管は作らない。漏えいが疑われる場合は値を公開せず運営者へ報告し、失効・削除等は別途承認する。現在のフィルター変更で過去分が消えたとは扱わない。

### Netlify経由のIP制限に関する現在の制約

Netlifyの `/api/*` リバースプロキシ経由では、Fly.ioが信頼する `Fly-Client-IP` はNetlifyの送信元IPとなる。同じ送信元を通る利用者間で登録・ログイン・回答のIP単位の上限を共有する場合がある。直接Fly.ioへ到達する要求ではFly ProxyのIPを使用する。任意の `X-Forwarded-For` や `X-Nf-Client-Connection-Ip` を無条件に信用しない。

Private解除前、又は共有による429が問題となった場合は、[Netlifyの署名付きプロキシ](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/)を設定し、APIで `x-nf-sign` を検証してから転送された利用者IPを採用する。現在の移行で新しいプロキシ秘密鍵や未検証のヘッダー信頼を追加しない。

## デプロイと障害復旧

### クレジット消費を抑える一括反映

ローカルで実装・テスト・型検査・ビルドを完了する。今回の移行・本番反映は一括承認済みであり、データ照合とFly.io切替後の最終main pushでNetlifyを1回だけ反映する。フロントの配信内容が変わらない場合は、承認済みのpushで `[skip netlify]` を使い、Netlifyを無理に再ビルドしない。フロントの比較判定は `frontend/netlify.toml` と専用スクリプトを使用する。手動実行・Build hookは別途確認する。販売開始、Private解除、APIの外部通知有効化は反映の承認と一緒に扱わず、それぞれの条件と承認を満たすまで変更しない。

### 反映と切戻し

1. 変更範囲とテスト結果・データ照合を確認する。DB変更は切戻し可能性と新旧接続先を確認し、Fly.io切替を先に完了する。最終main pushまでNetlifyの中間反映を発生させない。
2. Fly.ioの全マシンが自然停止中の場合、リリース開始前に通常のhealthアクセスで起動を確認する。リリース待機中は担当者が一時的に通常アクセスを確認し、終わったら終了する。永久ポーリングやmin_machinesの引上げへ無断で変更しない。
3. リリースがlease保持中に502になっても、進行中のleaseを強制解除したり並行再デプロイしたりしない。リリースの終了・失敗とlease解放を確認してから通常アクセスで復帰を確認する。現在はseedを実行しないため、長時間待つ場合はDB準備・接続・ロック待ちを調べる。
4. APIのhealth、公開問題、未認証の保護API、CORS許可・拒否を確認する。必要な会員操作は承認済みの確認アカウントだけで行う。
5. NetlifyのPublishedコミットとPrivateを確認する。資料だけのコミットがCanceledの場合は、実際の配信コードとの差分とキャンセル理由を区別して記録する。
6. 新旧で認証方式が異なるため、Netlify単独を旧版へ戻して互換性が保てるとは扱わない。旧版へ切り戻す場合は旧APIイメージ・旧DB接続・旧フロントの対応を確認し、Privateを維持して一連の切替として実施する。新DBを旧DBへ上書きしない。
7. API障害ではリリース状態・health・設定不足・DB疎通を確認する。直前のAPI版へ戻す場合もマイグレーション互換性を確認し、安易にDBを巻き戻さない。
8. 旧Vercelへの切戻しは、保護済み成功版の特定、アクセス保護とCORSの個別再許可を確認してから判断する。Git連携を自動で復活させない。旧版の削除期限は未決定のため削除しない。

## 問題データの編集と新規環境への移送

2026年10月21日のユーザー承認により、実行用seedとデプロイ時の問題同期を廃止する。既存DBを正本とし、訂正・非公開化・削除は管理画面から行う。`db:seed` は何もしない。通常のデプロイで問題が増減・上書きされることはない。

### 問題だけの書き出し

ローカルのコンテナ内で、存在しない出力ファイルを明示する。`tmp/` はGit管理外であり、出力は0600となる。親ディレクトリの閲覧権限も制限し、共有先・保存期間を決める。出力パスはコンテナ内のパスである。

```sh
docker compose exec -T -e OUTPUT=tmp/questions-export.json frontend npm run operations -- questions:export
```

- DBはrepeatable-read・read-only transactionで読み、問題・選択肢・公開状態だけを出力する。件数・形式バージョン・SHA-256を記録するが、本文を標準出力へ出さない。
- 同じファイルへの上書きは拒否する。SHA-256は転送・破損の照合用であり、送信元の真正性や承認の代用ではない。信頼した経路でファイルと照合値を受け取る。
- ユーザー、認証情報、決済、履歴、お気に入り、レコードIDを含まない。利用者データやIDを保持する復旧には、承認済みの完全DBバックアップを使用する。
- 本番の取得・バックアップには非公開運用側の承認済み手順を使う。本節を根拠に本番DBを無断で取得・書き戻ししたり、新しい保管・通知先を追加したりしない。

### 新しい空環境への明示取込み

問題と選択肢が両方空の環境だけが対象。接続先を確認し、承認済みアーカイブをその環境へ安全に配置した後に実行する。以下はローカル開発環境用の例であり、既存ローカルDBへは取込みできない。空にするための削除は行わない。

```sh
docker compose exec -T -e INPUT=tmp/questions-export.json -e CONFIRM=IMPORT_INTO_EMPTY_DATABASE frontend npm run operations -- questions:import
```

- 形式・件数・チェックサム・重複番号・4択・正答1件を検査し、公開問題には本文・出典・空欄等とセットの問1〜20登録検査も適用する。公開・非公開・下書きを保持する。
- 明示確認がない場合や、既存問題・選択肢がある場合は拒否する。途中で失敗した場合は全件ロールバックする。既存DBへのmerge・上書き同期は提供しない。
- 取込み後は出力件数と元の照合値を確認し、公開構成を `config/exam.json` と共通カタログに照合する。管理者ログインや会員・決済設定は別途準備する。

### 問題ID・日時を保持する今回の移行

通常アーカイブはIDを含めず、新規環境への問題移送用である。今回の移行は別形式 `schema_version: 1`、`questions` と `question_choices` の全列を持つ非公開JSONを使用する。

```sh
docker compose exec -T -e INPUT=/secure/path/question-identity.json -e CONFIRM=RESTORE_QUESTION_IDENTITY_INTO_EMPTY_DATABASE frontend npm run operations -- questions:restore_identity
```

例のパスはコンテナ内で読める保全済みファイルを指定する。移行先はPrisma Migrate適用済みで、ユーザーを含むアプリケーション表がすべて空であることが必要。ID・関連・分類・正答1件・公開セットの完全性を検証し、トランザクションとロックの下で取り込む。JSONBと `timestamp(6)` は変換で欠落させず、全列の照合と採番の再設定まで行う。失敗時は全件ロールバックする。

取込み後は件数・全列ハッシュ・問題URL・公開状態を元の保全データと照合する。管理者は新しく作成し、ユーザー採番は旧Stripe metadataと衝突しないことを確認する。実問題データをGitへ追加せず、通常の起動・リリースへこのコマンドを組み込まない。

### 旧Railsでのseed廃止確認記録

以下の2026年10月21日の記録は旧Rails版の当時の検証であり、新Node/Nitro版の実施結果ではない。


1. 最終承認内容が本番に反映されていることを読み取りで確認し、利用可能な暗号化バックアップと復元手順を確認する。ローカルの一致だけで本番一致としない。過去に成功した完全バックアップの記録と、今回の最新状態の確認は区別する。
2. 新版のrelease commandが `db:prepare` だけであることと、`test/` が本番イメージへ入らないことを確認する。未初期化DBの `db:prepare` と手動seedでも0問のままになる。
3. 新版デプロイ後、問題・公開状態と関連データの件数・全属性ハッシュ及び管理APIの通常動作を確認する。管理者の実データを検証のために書き換えない。
4. `question_seed_states` は今回は削除しない。release中の旧版や切戻し候補が表を参照するためである。旧版の稼働・切戻し期間終了後に、別途承認したマイグレーションで撤去する。
5. 旧版へ切り戻すと自動seed同期が復活し得る。切戻し時もrelease commandを明示確認し、管理画面で編集済みのDBへ旧seedを再投入しない。

原典fixture・承認記録・旧問題カタログはテスト専用として保存する。`test/fixtures/approved_question_catalog/` は凍結回帰資料であり、新規環境への投入元ではない。通常の訂正に合わせて過去の承認ハッシュを書き換えない。

### 廃止版のローカル検証（2026年10月21日）

- 旧50セットと固定比較値の51ファイルは移設前コミット `3aa6f15` と全バイト一致。承認snapshot・原典fixture・過去の固定ハッシュは変更していない。
- 既存ローカルの全1,000問・4,000選択肢・公開状態は承認カタログと一致。DB準備と手動seed2回の後も、問題・選択肢・履歴・お気に入り・ユーザー・決済・資格・Webhook記録の9モデルで全属性ハッシュが不変。アプリをeager loadしても旧同期クラス・旧状態モデル・旧payload変換は読み込まれなかった。
- 検証前に権限0600・専用ディレクトリ0700でローカル一時バックアップを取得した。検証終了後にも9モデルの不変性を再確認し、個人情報を含むその一時コピーだけを削除した。元DBは保持されており、本番の暗号化バックアップや非公開運用設定は変更していない。
- 別名で新規作成した隔離ローカルDBでは、初回 `db:prepare` と手動 `db:seed` 2回の後も問題・選択肢は0件。既存ローカルから読み取り専用で書き出したアーカイブを取り込み、1,000問・4,000選択肢を復元できた。再書き出しの全payload及びチェックサムが元と完全一致した。一時DBと復元用作業フォルダは検証後に削除済み。
- バックエンド全体492件・89,924検証を1回実行し、旧テストの準備に依存する5件の不一致を検出した。2件は廃止した削除tombstoneを過去の検査用設定として明示し、3件は大量回答の検査が本物の回数制限へ達しないよう隔離テストDBの一時カウンターを問題ごとに初期化した。実運用の制限値・認可・全選択肢判定・回答前秘匿の検査は変更していない。
- 修正した5件は再実行で24,842検証すべて成功。保存・削除・移送・既存同期行を無視する契約・回数制限の重点35件も290検証すべて成功した。変更対象の再検証で不一致は解消しており、全体492件の2回目の実行は行っていない。
- この確認はローカル限定。本番の最終内容照合・デプロイは実施しておらず、コミット・pushも別途の承認対象。完全DBバックアップの既存の暗号化・隔離復元記録を、今回の本番最新状態を確認した証拠とは扱わない。
