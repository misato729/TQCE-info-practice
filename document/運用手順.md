# 公開前の設定・運用手順

対象: Issue #6〜#9。手順の整備と実サービスでの検証完了は区別する。実施結果は [公開前運用確認](公開前運用確認_2026-10-20.md) に記録する。

## 変更しない前提

- 公開前はNetlifyの本番・プレビューをPrivateにする。Fly.ioのAPIは別の公開口であり、CORSだけでアクセスを制限できるとは扱わない。
- 販売開始の承認と下記の確認が完了するまで `PAID_MEMBERSHIP_ENABLED` を有効にしない。
- 問題の総点検中は `db:prepare && db:seed` と15分のrelease timeout、同期保護を維持する。障害対処のためにseedや検証を省略しない。
- デプロイ、バックアップ確認、決済照合だけを理由に、本番問題・会員・履歴を削除しない。

## 読み取り専用の点検

バックエンドで `bin/rails operations:audit` を実行する。本番ではFly.ioの対象アプリへ接続してから実行する。追加の公開APIやフロントエンドのポーリングは設けない。

出力は設定不足の項目名、販売の有効・無効、集計件数、警告名と確認日時だけとする。メールアドレス、ユーザーID、Stripe ID、DB接続文字列、秘密値は出さない。DBトランザクションは読み取り専用で、Stripeへの通信や決済・資格の変更は行わない。

| 項目 | 確認内容 |
| --- | --- |
| `payment_configuration_issues` | 必須設定の不足、キーと実行モードの不一致、戻り先URLの不正、本番のテストモード |
| `stale_pending_checkouts` | 作成から24時間以上経過した未完了決済。障害と断定せず、Stripe上のSessionと照合する |
| `refund_failures_last_day` | 過去24時間に返金失敗を受信した決済 |
| `disputed_payments` | 異議申立て状態の決済。解決済みでも手動確認待ちを含む |
| `active_memberships_with_revoked_payment` | pending・expired・refunded・disputedの決済を根拠に有効になっている資格 |
| `processed_webhooks_last_day` | 過去24時間の処理済みWebhook件数。0件だけでは障害と判断しない |

警告がなければ終了コード0、決済状態に確認対象があれば2、実行自体の失敗は非0とする。販売を止めている期間の設定不足は、障害ではなく販売準備の残件として扱う。定期実行と通知は別途設定が必要で、このコマンドを追加しただけでは有効にならない。

## Stripeの販売開始条件

1. Stripeのテスト環境で、購入成功、未完了・取消、同じWebhookの再送、重複購入防止、全額返金、異議申立てを確認する。ローカルの模擬応答テストと実Stripeの試験は分けて記録する。
2. 本番のProduct・Priceが日本円500円・一回払い・有効であることを確認する。`STRIPE_SECRET_KEY`、Price、Webhook送信先・署名シークレットを同じ本番モードにそろえ、`STRIPE_LIVEMODE=true` とする。
3. `FRONTEND_URL=https://luminous-piroshki-d94b2b.netlify.app` とする。成功時は `/premium/complete`、取消時は `/premium?canceled=1` に戻る。HTTPSのオリジンだけを指定し、認証情報、パス、クエリ、フラグメントを入れない。ローカルのHTTPはlocalhost/127.0.0.1だけを許可する。
4. Webhook送信先は `https://tqce-info-practice.fly.dev/api/v1/webhooks/stripe` とし、README記載の7イベントを登録する。署名不正400、正しい通知200、再送時の非重複を確認する。
5. 販売者名、責任者、住所、電話番号、連絡先、提供内容・時期、返金条件、利用規約とプライバシーポリシーを運営者が最終確認する。仮の連絡先や架空の事業者情報では開始しない。
6. バックアップ・復元、監視通知、HTTPS・認可、応答性能の公開前残件を解消する。運営者が販売開始を承認した後にだけ販売フラグを有効にする。
7. 有効化後に公開販売設定と導線を確認する。本番の実決済が必要なら金額・実行者・返金の扱いを先に承認し、検証用資格で代用したものを購入試験済みとしない。

販売設定に問題があればフラグを無効へ戻す。既存購入者の資格を一括で削除したり、支払済みの記録を手動作成したりしない。キーや事業者情報の値はIssue・コマンド履歴・ログへ貼らない。

## Webhook・決済の障害対応

| 状況 | 確認と対応 |
| --- | --- |
| Checkoutで502 | Fly.ioの時刻・request IDと `Stripe Checkout Session creation failed` を確認。Stripe側の障害・キーとモード・通信状態を確認する。連打で別決済を作らない |
| Webhookで400 | 署名、対象endpoint、実行モード、金額・通貨・metadataの照合を確認。署名検証を外して通さない |
| Webhookで500 | `Stripe webhook processing failed` と例外クラスを確認。Stripe Dashboardの対象イベントと送信履歴を照合する。DB更新はロールバックされるため原因を解消して再送する |
| 支払済みなのに資格反映待ち | Stripe上のSession・PaymentIntent・対象ユーザーの対応を権限のある画面で確認する。対象の署名済みイベントを再送し、同じEvent IDで重複がないことを確認する |
| 返金・異議申立て | 決済とStripeの状態を照合する。全額返金・異議申立てで資格を停止する仕様を維持する。異議申立て終了後の資格再開は自動では行わない |
| 24時間超のpending | Sessionを取得して未完了・expired・completeを確認する。既存の `PendingCheckoutExpirer` の仕様に従う。支払済みを単にexpiredへ書き換えない |

再送はStripe Dashboardの対象イベントから同じ送信先へ行う。本文をコピーして署名を偽造したり、DBへ有料資格だけを書き込んだりしない。再処理後は決済1件・購入資格1件、処理済みEvent IDの重複なしを確認する。テスト環境で先に実施し、本番への金銭操作やデータ修正は個別に承認する。

### 監視設定案と未設定事項

担当はリポジトリ所有者を一次窓口とする。実際に受信できる通知先・サービスと費用は未確認のため、新規契約や通知先の推測はしない。次を初期設定案とし、実サービスで通知到達・復旧通知まで試験してから有効とする。

- 外形監視はAPI healthを5分ごと、90秒以内に成功しない状態が2回連続したら通知する。スリープ復帰の1回だけで通知しない。実行間隔とAPI起動費用を確認する。
- 5xxが5分内に3回以上、Stripe API失敗又はWebhook処理失敗が1回以上で通知する。認証失敗4xxや無効署名を同じ障害条件にしない。
- 決済集計は1日1回を案とし、警告2の内容を照合する。既に確認済みの異議申立てを毎回新規障害として通知しない。
- 通知には時刻、アプリ名、状態、request ID、管理画面へのリンクだけを含める。パスワード・Cookie・Authorization・カード情報・Webhook本文は含めない。

## バックアップと復元

### 本番で先に確認すること

Neon Consoleの対象プロジェクトで契約プランと `Settings > Instant restore` の実設定を確認し、history window、保持量の制約、復元方法を記録する。公式資料の上限だけから現在の設定を推測しない。接続は直接接続（非pooler）を使い、DB接続先・パスワードをIssueや共有ログへ出さない。

初期の復旧目標案は、障害直前の復元可能範囲についてNeonの実設定に従い、別保管の論理バックアップは日次・7日保持、RPO 24時間以内、RTO 4時間以内とする。これは未承認・未達成の運用目標で、現在のサービス保証ではない。管理された暗号化保存先、復号鍵の別保管、運営者だけの閲覧、失敗通知、保存容量と費用を確認してから定期実行を設定する。バックアップは個人情報・パスワードハッシュを含むためGitや公開成果物に保存しない。

### 論理バックアップの手順

1. 対象DB、直接接続、バックアップ用権限、空き容量を確認する。接続情報は権限制限したPG service/passfile等で与え、URLをコマンド引数・共有ログへ埋め込まない。
2. DB、`pg_dump`、`pg_restore` のメジャーバージョンをそろえる。新しいツールで古いDBをdumpできても、古いDBへ復元できるとは限らない。
3. `pg_dump --format=custom --no-owner --no-acl` で全スキーマを取得する。問題だけに絞らず、users、履歴、お気に入り、決済、購入資格、検証資格、Webhook処理済み記録、同期記録も含める。
4. 制限された作業ディレクトリ（0700）・ファイル（0600）と承認済みの暗号化方法を用いる。実行時刻、ツール版、終了コード、暗号化済みファイルのサイズ・ハッシュだけを記録する。終了コード非0や空ファイルを成功扱いしない。
5. 一時名から完了名へ切り替え、保存先で読取り権限と復号可能性を確認する。定期実行後は最終成功時刻も監視する。復元検証前に古い成功分を削除しない。

### 隔離環境への復元

1. 本番・既存開発DBとは別の空DBを作り、接続先を二重に確認する。名前の付け替えだけで本番URLを流用しない。
2. 外部送信、実Stripeキー、Webhook受信、定期ジョブ、販売を無効にする。本番データを使う場合はアクセス権を限定する。
3. 復号したdumpを `pg_restore --dbname <隔離した新DB名> --exit-on-error --single-transaction --no-owner --no-acl <dump>` で新DBへ戻す。接続先を明示し、既存DBを `--clean` で上書きしない。失敗したDBをアプリへ切り替えない。
4. 全テーブルの件数・内容照合、外部キー・一意制約・CHECK制約、4択と正答1件、選択肢と履歴の対応、お気に入り、支払と資格、返金・異議申立て、Event ID重複防止、検証資格の期限・取消、管理者権限を確認する。
5. 隔離したアプリからログイン・問題・履歴・お気に入りを確認する。復旧対象時刻、検証者、所要時間、失う更新範囲を記録する。本番への切替は運営者の承認後に別作業として行う。

### ローカルの架空データによる復元検証

通常のDocker開発環境を準備した後、リポジトリ直下で実行する。

```sh
bash scripts/restore-drill.sh
```

ローカルにある公式 `postgres:16` イメージからツールだけを取り出す。未取得の場合は先に `docker pull postgres:16` で取得する。既存のバックエンドの一時ディレクトリで使い、通常のアプリ用ツールやDBサーバーを置き換えない。一時DBを新規に2件作り、現行スキーマと架空のユーザー・管理者・問題・4択・履歴・お気に入り・支払・資格・Webhookを投入する。custom dumpからもう一方へ復元し、全テーブルの件数と内容ハッシュ、制約・インデックス・シーケンス、関連を照合する。ダンプ、一時DB、ツールと一時コンテナは終了時に除去する。test環境かつローカルホスト以外では拒否し、既存DBへは投入・復元しない。

出力の `data: synthetic_only` は本番バックアップの検証ではないことを示す。本番の定期バックアップ・復号・復旧目標の達成確認は別途必要である。

## セキュリティ・ログ・応答性能

- Fly.ioのHTTPS転送、NetlifyのTLSとPrivate、会員・有料・管理者のAPI認可を維持する。フロントの認証CookieはproductionでSecure、SameSite=Lax。APIへのBearer送信に使うためHttpOnlyではなく、HTMLを直接挿入しない実装とトークン非出力も維持する。
- Railsログはstdout・既定info・request ID付き。Fly.ioアプリ／組織のログ閲覧権限、保存先・保持期間・外部転送、過去の漏えいの有無は管理画面で別途確認する。現在のフィルターが過去ログも消したとは扱わない。
- レート制限は現時点では未導入。公開APIのため、会員登録・ログインの総当たりと大量登録、回答の大量実行、Checkout連打のリスクがある。PrivateはAPIを保護しない。公開前に認証を優先し、共有カウンターを使う方式又はAPI前段の制限を選定する。プロセス内MemoryStoreだけを全マシン共通の制限と称して導入しない。
- 初期の制限案はログイン20回/5分/IP、登録5回/時/IP、回答120回/分/IP、Checkout10回/5分/ユーザー。学校などの共有IP、正常利用、複数マシン、偽装ヘッダー、期限後の解除、429とRetry-Afterを試験して調整する。これらは未適用の案で、観測データと方式の確認後に実装する。
- 応答の初期基準はウォーム時の問題取得・回答・履歴3秒以内、スリープ復帰時90秒以内、表示中の操作を妨げるエラーなし。スリープの遅延は許容する。少数回の測定をp95や全利用者の保証とせず、自然停止後と通常時を区別する。本番を強制停止して測定しない。

## デプロイと障害復旧

1. 変更範囲とテスト結果を確認する。DB変更があれば互換性と復元可能性も確認し、mainへpushする。自動リリースの重複実行を避ける。
2. Fly.ioの全マシンが自然停止中の場合、リリース開始前に通常のhealthアクセスで起動を確認する。リリース待機中は担当者が一時的に通常アクセスを確認し、終わったら終了する。永久ポーリングやmin_machinesの引上げへ無断で変更しない。
3. リリースがlease保持中に502になっても、進行中のleaseを強制解除したり並行再デプロイしたりしない。リリースの終了・失敗とlease解放を確認してから通常アクセスで復帰を確認する。seedの15分待機を短縮しない。
4. APIのhealth、公開問題、未認証の保護API、CORS許可・拒否を確認する。必要な会員操作は承認済みの確認アカウントだけで行う。
5. NetlifyのPublishedコミットとPrivateを確認する。資料だけのコミットがCanceledの場合は、実際の配信コードとの差分とキャンセル理由を区別して記録する。
6. フロント障害はNetlifyの直前の保護済み成功デプロイへ戻す。DB復元やRailsの再デプロイを同時に行わない。自動公開による再上書きにも注意する。
7. API障害ではリリース状態・health・設定不足・DB疎通を確認する。直前のAPI版へ戻す場合もマイグレーション互換性を確認し、安易にDBを巻き戻さない。
8. 旧Vercelへの切戻しは、保護済み成功版の特定、アクセス保護とCORSの個別再許可を確認してから判断する。Git連携を自動で復活させない。旧版の削除期限は未決定のため削除しない。
