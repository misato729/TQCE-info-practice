# 旧仕様との互換性・API通信の総点検（2026年10月25日）

## 比較対象と境界

- 移行直前のフロントエンド `882c898`（`dbdfbbd^`）、ローカル保管した旧Rails、現行 `5174ab9` と今回の修正を比較した。
- 要件定義・画面一覧・API設計・DB設計と、画面・API・テストを照合した。認証方式のBetter Auth化、Prisma化、承認されたユーザー等のリセットは意図的な変更として区別した。
- サイドバーは最新の指示を正本とし、未ログイン・無料会員は5セット、プレミアム会員・管理者・有効な検証用資格は50セットとする。10月24日の点検記録にある「全員50セット」は当時の記録で、現在の仕様ではない。
- Netlify・Fly.ioへのデプロイ、本番DB操作、実Stripeへの決済・返金・通知、旧DB・バックアップの変更は行わない。コミット・pushは別途の明示的な依頼に従う。

## 発見した問題と対応

| 項目 | 分類・対応 |
| --- | --- |
| ログイン・会員登録後の本人情報二重取得 | ローカル操作で完了した `/me` と、その成功を知らせるBetter Auth通知で再び実行した `/me` が重複していた。同じ成功操作の通知1回だけを共有し、追加取得を省略。別タブ・別セッション、失敗・競合・古い応答の保護は維持した。 |
| 管理編集の保存後GET | 旧版からある重複。PATCHが返す保存済みデータを画面へ反映し、同じ詳細を再GETしない。初回取得・手動再読込・サーバーの入力検証は維持した。 |
| 既知の不正な演習URL | 旧版からの改善。番号0、設定上限超過、選択条件外など、画面で不正と確定する位置は通信前にエラーとする。正常な取得・キャンセル・認証変更時の再取得、既存のエラー表示・再読み込み操作は維持した。 |
| 認証APIの接続表示 | Better Auth SDKの通信が接続ステータスへ接続されておらず、認証で通信障害が起きても正常表示が残り得た。公式fetchアダプターから既存の状態管理へ接続し、追加の確認通信なしで反映する。4xxは接続可能、5xx・通信失敗は赤、操作によるキャンセルは障害扱いしない。 |
| 資格変更後の履歴表示 | 旧版にもある潜在不整合。同じユーザーの資格変更を検知した時点で旧カードを破棄し、必要な一覧を1回取得する。再取得が失敗しても旧有料本文を復活させない。 |
| お気に入り操作の遅延応答 | 旧版にもある潜在不整合。別会員・資格・ページへ切り替えた後の成功・失敗・finallyで、新しい件数・エラー・処理中状態を上書きしない。解除・戻す操作は各1通信で、確認GETは追加しない。 |
| 決済確認と検証用資格の混同 | 旧版にもある不整合。購入の `membership.status = active` と、検証用・管理者等の利用権限を区別する。購入していない資格に「買い切り購入が確認」と表示しない。初回は強制確認を維持し、取得に失敗したときも古い資格だけで確認済みと判断しない。多重起動・画面離脱後の確認は防ぐ。 |
| 同じリクエスト内の資格SQL | HTTPとは別の重複。`/me` は取得済みの会員・検証資格を共有し、有料問題の取得でも同じ資格照会を繰り返さない。リクエストをまたぐ資格キャッシュは設けず、次のAPIでは現在のDBを確認する。 |
| 不正CookieのAPI資料 | 資料だけが匿名扱いと記載されていた。実装・旧Rails・既存テストと同じ401及び無効Cookieの破棄へ記述を合わせた。ログイン中の回答を匿名扱いして履歴を失う変更は行わない。 |
| 開発画面の初期化遅延 | Reka UIが開発時の事前バンドルから除外され、診断時に194個の部品ファイルが読み込み待ちになった。Viteのclient設定だけでRekaを事前バンドルし、個別ファイルの取得を0、バンドルの取得を1にした。SSRのtranspile、VueとNuxt UI本体の除外設定は維持する。初回の他モジュール変換には引き続き時間がかかる。 |
| ブラウザテストのAPI待受範囲 | 一部の `**/api/**` が開発時の依存モジュールURLにも一致し得た。実APIのpathnameを先頭から判定するよう修正し、JavaScript資源を合成API応答に差し替えない。 |

## 通信回数の確認対象

共通認証の初回確認・Better Auth標準のフォーカス復帰や別タブ同期を、一覧用の通信と混同しない。以下の「追加0」は、その操作のための業務APIを増やさないという意味であり、初回のCookie認証確認を省略したという意味ではない。

| 操作 | 確認する通信 |
| --- | --- |
| サイドバーの一覧表示・開閉 | 問題・試験一覧・ヘルス・サイドバー独自の会員確認は0回 |
| ログイン・登録の成功後 | 操作に必要な `/me` は1回。同じSDK通知による再取得なし |
| 同じアプリ内で試験概要・利用規約へ移動 | 業務APIの追加0回 |
| 無料会員のお気に入り案内 | お気に入り一覧GETは0回（料金機能無効の合成テスト設定では一覧を許可） |
| 利用資格がある会員のお気に入り・履歴 | 各一覧を1回取得し、既知の会員情報は共有 |
| お気に入り解除・戻す | DELETE・PUT各1回、確認用の一覧GETなし |
| 管理編集の保存 | PATCH1回、保存後の詳細GETは0回 |
| 不正な演習位置・その再読込 | 問題取得APIは0回 |
| 条件指定演習 | 各位置の問題取得1回、回答POST1回。完了ボタンで次問取得を追加しない |
| ランダム演習の再読込 | URLのseed・位置を維持し、その位置を1回取得する |
| 決済結果の初回確認 | 返金・失効を見落とさないため `/me` の強制取得1回を維持。古い共有状態だけで確認済みと判断しない |
| 未反映の購入確認 | 画面を開いている間だけ最大8回・1.5秒間隔。離脱・別会員へ切替後は継続しない |

資格SQLの回数は、ユーザー・問題・お気に入り等を除いた会員資格／検証資格の照会だけを数える。料金機能が有効な一般会員では、`/me` は各2回から各1回、有料問題の `/questions/next` は合計6回から2回に削減した。回数はPrismaのテスト用delegateとコード照合で検証したもので、DBログの物理SQL計測ではない。無料位置の不正パラメーター・候補なしなどの早期終了で資格照会を増やさない。

## 維持した機能と意図的な差

- 問題URL、問1〜20、教職教養／情報科の分類、条件指定・順序・random seed・終了導線を照合した。試験概要・法的ページ・コンテンツ表示・標準レイアウト・順序処理は移行前と同じ構造を維持する。
- 回答前の正答・解説非公開、選択肢の所属検査、匿名回答の非保存、本人だけの履歴・お気に入り、非公開問題の排除、資格失効時のAPI拒否を維持する。
- 一般／管理で同じ認証を使用し、現在DBのadmin role、管理入力検証・公開条件、問題編集時の履歴整理と選択肢ID維持を照合した。
- Stripe署名、金額・商品・所有者・live/test照合、二重処理防止、返金・異議申立て、削除時の決済整理を合成データと隔離DBで確認する。実決済や本番の販売状態は変更しない。
- 認証APIの経路とCookie方式、設定による試験番号上限50、一部の不正入力を早期に拒否する差は、承認済みの構成変更として維持する。
- 決済・販売者情報の実行時API、履歴詳細の問題取得と履歴取得、必要な認証同期、運用のヘルスチェック、通信失敗時の既存GET再試行は用途があるため維持する。API仕様が全入力を必要とする管理一覧の公開切替も、認可・整合性を崩して通信だけを減らさない。

## 検証結果

ブラウザでの通信回数検査は合成応答を用い、登録・Cookie・保存等の実動作は隔離した実API／PostgreSQLの検査と区別する。

- 最終修正を含むフロントエンド全181件が成功。
- 問題取得の資格SQL共有を含めたサーバー最終121件が成功。認証・認可・採点・履歴・お気に入り・管理・決済・マイグレーション・復元を隔離DBで検証した。
- アプリ・Nitroサーバー・Nuxt設定の型検査が成功。決済確認の追加修正後はアプリの型検査と決済関連12件も再確認して成功。
- 隔離した実サーバーでPC／スマートフォン46件が成功。登録・Cookie・履歴・お気に入り・再ログイン・別タブ認証・遅延応答・フォーム・通信回数を含む。
- 最終修正を含む通常Docker設定（50セット・会員資格の制限あり）でもPC／スマートフォン38件が成功。通信回数、決済確認失敗時の古い資格の扱い、5／50セット表示、条件指定・ランダム演習、別タブ認証を合成応答で確認した。デスクトップとスマートフォンの保存画像も目視確認した。
- 最初のサーバー検査前・隔離ブラウザ検査後・最終確認で、通常開発DBの問題1,000件・選択肢4,000件をREAD ONLYで全列照合し、SHA-256が一致した。テストは名前を制限した別DBだけに実施し、一時テストDBが残っていないことも確認した。旧DB・volume・バックアップは変更していない。
